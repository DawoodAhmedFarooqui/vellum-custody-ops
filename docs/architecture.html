Custody Ops Console: how it is built and why

A back-office web app for Vellum Fund Services' operations team: clients, transaction approval, monthly fee invoicing and custodian file import. This document explains the problem as understood, the architecture, the data model and the mechanisms behind the hard requirements.

1. The problem

About 2,000 clients hold 3,030 portfolios. Fifty thousand transactions from January to September 2026 arrive from the custodian bank and need checking. Every month each client is billed from a fixed fee schedule. Six staff use the app all day, with three levels of authority:

RoleUsersMay do

The brief's hard requirements, beyond the features themselves: links must reopen the exact grid view; grids must stay fast on the full data; two operators editing one client must not overwrite each other silently; bulk actions must explain what happened to each row; invoices must reconcile to the cent and be unique per client and month; imports must survive the same file being uploaded twice.

2. System architecture

Why this shape: a single origin removes CORS and lets the session cookie be SameSite=Strict, which also covers CSRF. The server applies schema.sql idempotently on each start and seeds once, guarded by a marker row taken with FOR UPDATE, so even two server instances starting together load the data exactly once.

3. Data model

4. Grids: the URL is the state

Each client tab is a nested route (/clients/C-00001/transactions?status=SETTLED), and a deep link opened while signed out returns to that exact location after login. Pagination is server-side; a page of 50 rows deep into the 50,000 transactions returns in well under 100 ms.

5. Two operators, one client: optimistic locking

6. Bulk approve and cancel

Operators tick rows and press Approve or Cancel. The server locks the selected rows (SELECT … FOR UPDATE), updates only those still PENDING, writes one audit entry per changed row, and returns an outcome for every requested id: UPDATED, SKIPPED (with its current status) or NOT_FOUND. The UI lists these in a table. Because the update is conditional on status = 'PENDING' under a row lock, two operators acting on the same transaction at once cannot both succeed; the second sees it skipped with the new status.

9. Security and roles

Sessions

  • Passwords stored as bcrypt hashes (cost 12)
  • JWT in an HttpOnly, SameSite=Strict cookie, 10 h
  • Unknown emails compared against a dummy hash, so timing reveals nothing
  • 5 failures lock that address + email for 5 minutes

Authorisation

  • Every /api route requires a session; the user is reloaded per request
  • Each write route names a permission; roles map to permission lists on the server
  • The UI reads the same list only to hide buttons; the server decides
  • Sort columns are whitelisted; all values are bound parameters

10. Audit trail

Every client edit, transaction status change (including imports) and invoice transition writes an audit_log row on the same database connection as the change, so the two commit or roll back together. Each row records who, when, the entity, the action and a field-level { from, to } diff. The client page's Audit log tab shows them newest first with links to the transaction or invoice involved.

11. How it was verified

  • 16 unit tests on the two pure modules: fee maths (rounding, clamps, FX, reconciliation) and the import parser and validator.
  • Every API route exercised as viewer, operator and admin with valid and malformed input.
  • Four races run in parallel: concurrent client edits, approve vs cancel of one transaction, three simultaneous invoice generations, two uploads of the same file. Each produced exactly one winner and clean 409 responses.
  • A SQL check across all generated invoices: total = Σ lines = Σ item fees + account fee, every fee within 15–250 EUR.
  • A scripted browser walkthrough (Playwright on Chrome) against the Docker build from a wiped database.
  • docker compose down -v && docker compose up --build from scratch: 50,000 transactions loaded in about ten seconds.

12. Known gaps and the path to production

Not done

  • No automated API or end-to-end tests in the repo (verified by scripts, not CI)
  • Audit log is per client, latest 1,000 entries, no global view
  • No invoice PDF; portfolios and users are read-only
  • Single JS bundle, no code splitting

Before real client data

  • Secrets from a vault, TLS, security headers
  • Revocable server-side sessions, MFA for admins
  • Versioned migrations run at deploy time
  • CI: lint, unit, integration (testcontainers), e2e
  • Structured logs, metrics, readiness probe, backups
